# Operator runbook

The operator keeps evidence and promises in order. Krish makes relationship decisions and manually sends or publishes exact actions. Control Center owns private state; this repository supplies the repeatable method.

## Before the first real run

Confirm the intended Control Center tenant and authorised read/write scope through approved access. Never place credentials in a prompt, Git file or report. Verify current commercial sources, destination status, suppression handling, private artifact destination and duplicate prevention. Exercise the repository's synthetic workflow before recording activation. If a connector is unavailable, prepare a labelled private handoff for later review; do not claim synchronisation.

Assign a named operator in the private run record and agree a realistic review capacity with Krish. A missing operator is a visible capacity risk. It does not justify expanding send authority.

## Runtime commands

Run from the repository with Node 24 or newer. The runtime uses the approved managed environment for private access. Never put credential values in command arguments or chat.

| Command | Observable behaviour |
| --- | --- |
| `npm test` | Exercises synthetic regression fixtures; no live send or production mutation |
| `npm run check` | Runs repository integrity checks |
| `npm run demo` | Plans from the checked-in synthetic snapshot at its fixed fixture time; it demonstrates behaviour rather than current production state |
| `npm run doctor` | Reads the live private snapshot and validates the contract, canon and buyer definition; writes zero records |
| `npm run daily` | Reads live state and prepares a dry-run summary; commits nothing |
| `npm run daily -- --commit` | Writes a private draft batch to the approved Control Center adapter, then verifies its durable receipt; sends and publishes nothing |
| `npm run scorecard` | Reads private source state and reports the current week and, when configured, the first-month outcome |

Before first-month reporting, set `GROWTH_LAUNCH_DATE` to the actual activation date outside Git, or pass the actual `YYYY-MM-DD` date through `--launch-date` after the npm argument separator. Do not set it to the demo date merely to produce a scorecard. Keep live output and reports out of public CI logs. The `--output` option accepts a private output only inside the ignored `runtime/` directory; treat those files as sensitive despite Git ignoring them.

If a committed run is interrupted, inspect its durable receipt using the CLI `resume` command and the actual `--run-id` from the prior summary. Do not assume an interrupted write failed or replay it blindly. A receipt proves private draft persistence, not a message sent or a business result.

## Source freshness

The runtime pins the reviewed commercial contract and stops once that review is more than 30 days old, even if a fresh snapshot repeats the old facts. Refresh the underlying Mindmake sources, compare public claims and proof permissions, and review the versioned contract change through the normal code process. Update the reviewed content, source revision and review timestamp together only after that review. Never renew a date or alter a snapshot merely to bypass a stale-canon hold. The policy file also bounds snapshot, evidence and trigger age; those limits reduce stale preparation and do not establish that every claim is true.

## Daily pass

1. Read objections, suppression changes, inbound replies and delivery failures first. Stop affected actions and preserve the reason.
2. Identify requested information and agreed next steps due. Confirm ownership and timing before creating work.
3. Read relevant private relationship or prospect briefs. Run research against explicit questions, then store enrichment privately without creating a sales ranking from it.
4. Prepare at most five new named recommendations by default, with a hard maximum of ten per daily run. Reduce the limit if review capacity is lower. Attach evidence, artifact references and eligibility checks. Keep research-only notes out of the action shortlist. These are preparation limits, never sending quotas.
5. Give Krish an inspectable queue: recipient/account, reason now, complete draft, exact links or attachment, uncertainty, pending manual action. No hidden send or schedule step.
6. Record only observable outcomes: manually sent, published, replied, held, qualified, proposed, paid, closed. A queued artifact proves only preparation.

Use private stable identifiers to deduplicate a rerun. Before creating a new action, look for the same person, decision and purpose. Preserve edited drafts and the approved version; never silently replace wording awaiting review. A changed recipient, payload, channel or timing invalidates the old action approval.

## Weekly decision

Read the scorecard with evidence coverage and partial-window labels. Review each live opportunity's next decision, owner and date. Remove duplicate work through the private system's governed process; do not purge contacts or history. Close an opportunity only on evidence or an explicit operator decision with a reason.

Choose one constraint to address and, if useful, one reversible experiment. Decide whether one cleared learning merits a reusable aid or selected post. Refresh claim and channel status where a draft depends on them. A review date creates an operator reminder to assess, never a future send instruction.

## Failure handling

| Failure | Operator response |
| --- | --- |
| Private source inaccessible | Keep affected facts unknown and actions blocked; continue with independent authorised work |
| Contradictory evidence | Preserve both sources, omit disputed claims and route the decision to the owner |
| Duplicate action or replay | Reuse the stable reference and inspect authoritative state before a new write |
| Stale or changed draft | Return to review with the actual final payload |
| Suppression or objection | Stop contact across relevant channels immediately; record the preference in the authoritative system |
| Missing payment evidence | Report proof as pending commercial verification |
| Runtime fails | Retain private inputs and logs in their approved private location; use the playbook manually without pretending the run passed |

Before restarting after a failed write, inspect the destination. An unknown outcome is not a safe reason to repeat it. Never send a live message as a health check. Keep private operational records out of CI logs, pull requests and public issues.

## Stop at the real boundary

This runbook authorises preparation within the task scope. It does not authorise external messaging, publication, data imports, new subscriptions, ad spend, account changes or deletion. The useful deliverable at that boundary is a concrete reviewed artifact and a clearly named manual action.
